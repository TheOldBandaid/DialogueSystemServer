# Серверная часть системы управления диалогами игровых персонажей

Сервер на C# и ASP.NET Core с SQLite. В проекте есть веб-редактор, предпросмотр диалогов и примеры «Ключ от архива» и «Кино после патруля».

Требуется .NET 10 SDK. Команды выполняются в PowerShell из корня проекта.

## Запуск сервера

```powershell
.\Start-Demo.ps1
```

Адрес редактора — [http://127.0.0.1:5189](http://127.0.0.1:5189).

Скрипт проверяет учётные записи в базе, в том числе после прерванного первого запуска. Для отсутствующих начальных аккаунтов он запросит в терминале пароли длиной от 12 до 512 символов. Существующие пароли не меняются. В браузере войти как `editor` для редактирования диалогов или как `admin` для управления учётными записями.

Учётные записи, диалоги и история прохождений сохраняются в `artifacts/demo-data/dialogues.db`. Для создания недостающих учётных записей в существующей базе используется `.\Start-Demo.ps1 -InitializeAccounts`.

Оба скрипта принимают `-DataDirectory 'полный-путь-к-данным'`. Для запуска и обслуживания одной базы указывать одинаковый каталог. Параметр `-Port 5190` меняет адрес локального сервера. Прямой `dotnet run` без `DialogueSystem:DataDirectory` по-прежнему использует другой каталог `src/DialogueSystem.Web/App_Data`.

Один каталог данных одновременно использует один процесс сервера или обслуживания. Перед локальными командами обслуживания нужно остановить сервер; файл `server.lock` после остановки удалять не требуется.

Перед применением новых миграций к существующей базе сервер сохраняет согласованную копию SQLite в подкаталоге `backups` каталога данных. Если создание копии не удалось, обновление базы не начинается.

Ежедневная копия создаётся при запуске сервера и затем проверяется раз в час, пока он работает. День определяется по UTC. Копии проверяются командами SQLite `integrity_check` и `foreign_key_check`. Хранятся семь последних ежедневных, три копии перед миграциями и три перед очисткой истории. Ручные копии и файлы, сохранённые перед восстановлением, автоматически не удаляются. Автоматические ежедневные копии можно отключить настройкой `DialogueSystem:Backups:Enabled=false`; защита перед миграциями и очисткой остаётся включённой.

Для ручной копии или восстановления остановить сервер:

```powershell
.\Maintain-Server.ps1 -Action Backup
.\Maintain-Server.ps1 -Action Restore -File 'полный-путь-к-копии.db'
```

Восстановление проверяет точный снимок выбранной базы, её связи и совместимость миграций. Текущая БД и её журналы предварительно сохраняются отдельно в `backups/before-restore-*`. Замена выполняется SQLite Backup API. Все прежние cookie перестают работать, даже если восстановленная версия пользователя совпадает со старой cookie. Пользователи, пароли и роли возвращаются к состоянию копии; после восстановления запустить сервер и войти заново. Если база повреждена настолько, что SQLite не может открыть её для записи, сохраняется копия текущих файлов и команда завершается ошибкой — эти файлы можно убрать в отдельный каталог вручную при остановленном сервере и повторить восстановление.

До замены рабочей базы сервер подготавливает временную копию: проверяет последовательность миграций, применяет недостающие обновления и проверяет чтение всех таблиц приложения. Ошибка подготовки оставляет рабочую базу и сеансы без изменений. Исходный файл резервной копии не меняется.

Копии `.db` содержат все прикладные данные, включая аккаунты, версии и историю. Ключи защиты cookie в `keys` в них не входят: для восстановления данных они не нужны, прежние сеансы намеренно отзываются. Хранить копии следует в закрытом месте вне `wwwroot` и Git. Экспорт JSON одного диалога не заменяет резервную копию БД.

## Проверка в редакторе

1. Войти как `editor` и выбрать **Кино после патруля** в списке диалогов.
2. Нажать **Проверить диалог**. Появится сообщение «Диалог готов к предпросмотру».
3. В разделе **Предпросмотр** нажать **Начать с первой реплики**. Пройти сцену дважды, ответив на предложение Терры согласием и отказом. Оба прохождения появятся в **Истории прохождений**.
4. Выйти, войти как `admin` и открыть **Учётные записи**.

Списки диалогов, персонажей, реплик и пользователей показываются страницами по 20 записей. Для поиска использовать поле над списком, для продолжения — кнопку «Показать ещё». Поиск работает без учёта регистра, включая кириллицу. Текущий говорящий и цель ответа сохраняются в выборе, даже если находятся вне загруженной страницы.

## Восстановление доступа

Администратор может выдать другому пользователю временный пароль в разделе «Учётные записи», подтвердив действие собственным паролем. Прежние сеансы пользователя отзываются. Временный пароль позволяет только войти и сменить пароль; доступ к диалогам до смены закрыт сервером.

Если пароль администратора забыт, остановить сервер и выполнить локально:

```powershell
.\Maintain-Server.ps1 -Action ResetAdminPassword -Login admin
```

Команда попросит новый пароль и повтор без отображения символов. Она восстанавливает роль администратора выбранному существующему пользователю. Для другой базы явно указать `-DataDirectory`. Пароль не передаётся аргументом командной строки. Проверить начальные аккаунты можно командой `-Action AccountsStatus`.

Экспорт и новые сохранённые версии используют JSON версии 2 с ключами персонажей. Импорт файлов версии 1 поддерживается; в старом формате говорящие сопоставляются по имени.

При копировании диалога и открытии версии можно включить «Создать отдельных персонажей»: у копии будут собственные персонажи с новыми ключами. По умолчанию используется общий справочник, поэтому переименование общего персонажа влияет на все его живые реплики.

Если старый снимок содержит прежнее имя переименованного персонажа, создаётся отдельный вариант с этим именем. Последующие открытия того же снимка повторно используют вариант, пока его имя не изменилось. Разные исходные ключи не объединяются по имени. Старые дубли, созданные до появления сопоставления, автоматически не склеиваются: их происхождение нельзя надёжно восстановить по одному имени.

Чтение графа и использований персонажа выполняется в согласованной отложенной транзакции SQLite без резервирования записи. При сохранении версии загрузка и сериализация снимка выполняются до короткой транзакции записи; если за это время граф изменился, сервер отвечает `409` и предлагает повторить действие.

Сохранение и удаление защищены от устаревших действий в другой вкладке или у другого пользователя. Если данные изменились, сервер отклонит действие: обновить страницу, проверить актуальные данные и подтвердить намерение заново. Это относится к репликам, ответам, метаданным диалога, персонажам, переносу говорящего и ролям пользователей.

Список прохождений показывается по 20 сеансов, история — по 100 шагов с кнопкой продолжения. При удалении отдельной реплики история сохраняется, при удалении диалога удаляется вместе с ним.

Демонстрационный скрипт работает в Development на локальном HTTP-адресе. В Production HTTP перенаправляется на HTTPS, cookie сеанса получает `Secure`, а ошибки возвращаются без внутренних трассировок. Порт HTTPS по умолчанию — 443, его можно изменить настройкой `HTTPS_PORT`. При публикации нужно настроить сертификат HTTPS и закрытое хранилище каталога данных и ключей.

## Большие диалоги

Карта получает облегчённый снимок: все узлы и связи, но сокращённые подписи. Полный текст остаётся в экспорте и контексте выбранной реплики. В браузере пространственный индекс отбирает видимые элементы; DOM-узлы вне окна карты удаляются, canvas имеет размер видимой области. На плотных участках число стрелок ограничено с явным предупреждением; списки переходов выбранной реплики сохраняют доступ ко всем связям.

Входящие и исходящие переходы выбранной реплики показываются порциями по 20. Для продолжения использовать соответствующую кнопку под списком. Если связи изменились во время просмотра, обновить контекст реплики перед продолжением.

## Очистка истории и версий

В редакторе открыть «Очистка истории и версий», выбрать прошедшую дату, категории и число сохраняемых последних записей (1–1000). По умолчанию выбираются только свои завершённые прохождения; сохранённые версии включаются отдельно. Опция «Включить прохождения с удалённой текущей репликой» позволяет также очистить старые невозобновляемые сеансы. Она выключена по умолчанию и действует только при выбранной категории прохождений. Сначала нажать «Рассчитать очистку», проверить количества и подтвердить удаление. Записи без даты и незавершённые прохождения с существующей текущей репликой не удаляются. Дата сравнивается строго: удаляются записи старше выбранного момента. «Последние» определяются по дате начала и ID для прохождений, по ID для версий; защита применяется отдельно к каждой категории внутри выбранной области пользователей и действует также для сеансов с удалённой репликой.

Редактор очищает только собственные прохождения и версии со своим авторством. Администратор может явно выбрать данные всех пользователей. Рабочие реплики, персонажи и переходы очистка не затрагивает. История удаляется вместе с выбранным прохождением через внешний ключ с каскадом. Файл SQLite после удаления может сохранить прежний размер: страницы освобождаются для повторного использования; `VACUUM` на работающем сервере не запускается.

Перед удалением сервер повторно проверяет состав очистки и создаёт проверенную резервную копию SQLite. Ошибка копирования отменяет очистку. За один раз удаляется до 100 прохождений и 100 версий; если осталось больше, заново рассчитать следующую порцию и подтвердить её. При изменении данных прежний расчёт становится недействительным. Для восстановления базы использовать `Maintain-Server.ps1` при остановленном сервере.

## Тесты

Команда выполняется из корня проекта в новом окне PowerShell.

```powershell
dotnet test DialogueSystem.slnx
```

Для проверок форм редактора требуются Node.js 24.15 или новее и pnpm. Эти зависимости нужны только для тестов:

```powershell
cd tests/DialogueSystem.BrowserTests
pnpm install --frozen-lockfile --ignore-scripts
pnpm test
```
